# 压测报告（k6）

> 目的不是刷一个好看的数字，而是给「这套东西能扛多少」一个可复现的答案，
> 顺便验证两条护栏（AI 降级、配额限流）真的生效。
> 所有数字都能用 [perf/k6](../perf/k6) 里的脚本按「复现命令」重跑出来。

## 1. 环境与拓扑

| 项 | 值 |
|---|---|
| 机器 | Windows 11 + Docker Desktop 29.1.3（WSL2 后端） |
| 应用 | `isd:local`（`eclipse-temurin:21-jre-alpine`，`-XX:MaxRAMPercentage=75`），容器内 8081 |
| 数据库 | `mysql:8.0.36` 容器，本机环回，单实例 |
| 会话 | `redis:7.4-alpine` 容器，每个请求一次 Redis 往返（Spring Session） |
| 压测端 | `grafana/k6:0.54.0` 容器，与 app 同宿主机（经 `host.docker.internal`） |
| 数据集 | 2000 条工单（同一账号），预热后开压 |

**不是生产环境**：应用只有 1 个实例、MySQL 与 app 抢同一台机器的 CPU，
所以下面的数字应读作「本机上限」，不是容量承诺。

## 2. 场景与参数

| 场景 | 脚本 | 参数 | 每迭代请求 |
|---|---|---|---|
| 工单读路径 | `perf/k6/tickets.js` | constant-vus，10 VU，20s | 列表、关键词列表、详情（3 个） |
| AI 降级 + 配额 | `perf/k6/ai.js` | per-vu-iterations，1 VU，25 次 | 1 次 `/api/ai/chat` |

两个脚本都用固定 `Idempotency-Key` 造数据（`perf-seed-<n>`），重跑不会重复插入；
会话在 `setup()` 登录一次，之后每个迭代用 `cookieJar().set` 塞回（k6 每轮迭代会清空 cookie jar）。

> CSRF 双提交上线后，脚本在登录前会先 `GET /api/ping` 取 `XSRF-TOKEN`，再把同一个值放进
> `X-XSRF-TOKEN` 头——漏掉这一步，登录与建单都会被 403，压测会直接失败而不是"数字变小"。

## 3. 结果：工单读路径（预热后，2000 条数据）

| 指标 | 值 |
|---|---|
| 请求总数 | 3861（620 次迭代 × 3 + 种子 2000 的幂等重放） |
| 吞吐 | **116.4 req/s**（10 VU，单实例） |
| 失败率 | **0.00%** |
| 列表 p50 / p95 / p99 | 8.20 / **9.65** / 11.23 ms |
| 关键词列表 p50 / p95 / p99 | 8.22 / **10.19** / 11.29 ms |
| 详情 p50 / p95 / p99 | 5.93 / **6.82** / 7.38 ms |

冷启动对照轮（第一次跑，同时还在写 2000 条种子数据）：

| 指标 | 值 | 说明 |
|---|---|---|
| 失败率 | 0.12%（5/3861） | 集中在写入阶段 |
| 列表 p95 / p99 / max | 12.25 ms / 2.14 s / 2.14 s | 尾部延迟来自首轮 JIT 与连接池建连 |
| 关键词列表 p95 | 10.54 ms | 与预热轮差异在噪声范围内 |

结论：预热后 p95 全部在 12 ms 以内，尾部延迟消失。
**首轮 2 秒级的偶发尖刺不是接口问题，是 JIT + 连接池预热**——这也是"压测必须先预热再取数"的原因。

## 4. 结果：AI 降级与配额

| 观察 | 值 |
|---|---|
| 迭代数 | 25（1 VU 连续调用） |
| 200 + `source=FALLBACK` | 20 次（未配真实 Key，走知识库降级，**没有 5xx**） |
| 429（配额用尽） | 5 次，文案带剩余秒数 |
| `ai_server_error` | 0 |
| checks 通过率 | 100%（26/26） |
| 单次延迟 p95 | 47.7 ms（降级路径，无外网调用） |

这是**被验证的行为**而不是缺陷：配额 20 次/分钟，第 21 次起必须拒绝，
否则一个脚本就能把 token 额度刷穿。报告里把 429 单独计数，就是为了不把它误读成"接口挂了"。

## 5. 瓶颈分析

1. **`LIKE '%kw%'` 在 2000 行时还没显形**：关键词列表 p95（10.19 ms）与普通列表（9.65 ms）几乎一样。
   原因是数据量太小，MySQL 全表扫描 2000 行只要几毫秒。
   **结论要诚实**：这是"尚未暴露的扩展性风险"，不是"已验证没问题"——数据量到十万级时，
   这条路径会线性劣化，届时要么上 FULLTEXT（`kb_item` 已经这么做了），要么引入 ES。
2. **单实例 Tomcat 是当前吞吐上限**：10 VU 下 ~116 req/s，CPU 未打满（延迟仍在 10 ms 级），
   说明还有余量；真正到瓶颈时先看 Tomcat 线程池与 HikariCP 连接数，而不是盲目加实例。
3. **每次请求一次 Redis 往返**：会话外置的固定成本，本机测得亚毫秒级（`http_req_waiting` 与总延迟差距很小）。
   换来的是多实例部署下踢人/改密立即生效，这个交换在项目背景里是划算的。
4. **详情接口最快（p95 6.82 ms）**：主键查询 + 权限校验，符合预期；
   如果它变慢，第一时间查索引是否失效，而不是加大连接池。

## 6. 复现

```powershell
docker compose -f docker-compose.stack.yml up -d            # 全栈
.\perf\k6\run.ps1 tickets -Env @{ SEED_TICKETS = 2000 }      # 工单读路径
.\perf\k6\run.ps1 ai                                         # AI 降级 + 配额
docker compose -f docker-compose.stack.yml down -v           # 清掉压测数据
```

阈值写死在脚本的 `options.thresholds` 里：列表 p95 < 300 ms、关键词列表 p95 < 500 ms、详情 p95 < 200 ms、
AI 5xx == 0。**跑不过就是退出码非 0**，所以这些数字不会随代码改动悄悄失效。

## 7. CI 冒烟压测

`.github/workflows/ci.yml` 的 `perf` job 会在每次 push / PR 跑一轮冒烟，防止"某个改动让 p95 数量级退化"却没人发现。

| 项 | 完整压测（本文 3–4 节） | CI 冒烟 |
|---|---|---|
| 拓扑 | `docker-compose.stack.yml` | 同 |
| 并发 / 时长 | 10 VU / 20s | 5 VU / 5s |
| 种子工单 | 2000 | 200 |
| AI 迭代 | 1 VU × 25 次 | 同 |
| 阈值 | 脚本内 `options.thresholds` | **完全一致，不放宽** |
| 用途 | 出报告、找瓶颈 | 防回归，跑不过即红 |

只允许用 `VUS` / `DURATION` / `SEED_TICKETS` 缩短时间，不允许为了让 CI 变绿而改阈值——那等于把门禁关掉。
另外，GitHub 共享 runner 是 2 核且与容器抢 CPU，**绝对延迟不能和本机数字对比**；冒烟只保证没有数量级退化。
日志与退出码就是证据，失败时在 Actions 的 `perf` job 里能看到每个 threshold 的实际值与是否通过。
